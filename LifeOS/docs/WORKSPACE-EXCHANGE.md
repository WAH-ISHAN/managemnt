# Continue on another computer

Open **Devices & privacy → Continue on another computer**. Pair the computers using their public keys, compare the fingerprint on the receiving computer, and select a folder already shared by your own USB or cloud-sync software. Approve sharing this profile's private records and documents with that computer before enabling automatic delivery. No new cloud account or remote server is created.

LifeOS delivers a new encrypted snapshot when records change, at the chosen 15–1,440 minute interval while its resident process runs. **Deliver a snapshot now** uses the same path. The three most recent outgoing snapshots for that computer pair remain in the chosen folder. Other computers' snapshots and unrelated files are not removed. Delivery failures are visible on the page and retries respect the configured interval. A missing drive is a failure, not a successful sync. Nothing runs while the computer is asleep or LifeOS is stopped.

The receiving computer lists its snapshots from paired, nonrevoked devices. **Review received workspace** authenticates and validates a snapshot, then shows added/changed/removed record counts and document-file changes. It changes no user records. To apply it, type **REPLACE** and choose **Replace with reviewed workspace**. Reviews expire after 15 minutes; changed records or changed incoming bytes require another review. Replayed snapshots, another recipient, altered ciphertext, invalid schemas/files and revoked peers are refused.

This is **automatic snapshot delivery with reviewed workspace replacement**. It is not concurrent field-level merging. Work on one computer at a time. Use existing task or selected-record packets when you want a smaller, conflict-resolved merge. A snapshot replaces this profile's business/personal records and uploaded documents, including removals. It does not replace other local profiles or the installation registry. Both computers must have matching modules and migrations. The same bounded archive limits apply as complete encrypted backups: up to 256 MiB encrypted, 512 MiB expanded and 5,000 uploaded files.

Sharing includes financial/academic/work records, Knowledge notes, private journal/mood records and uploaded files. Device keys, browser state, AI account credentials and configured external credentials are not copied. Database settings, local profile/module preferences, API tokens, device relationships, connection mappings, trusted publisher/plugin records and executable automation definitions are excluded from outgoing snapshots. These distinctions do not redact secrets a person manually types into a note or document: the explicitly approved records are transferred as entered.

Local credentials, PIN/security preferences, paired devices, trust and automation definitions are retained during replacement. Sync mappings, connection history and edit history are reset because their numeric record identities belonged to the old workspace. Automatic sharing, calendar/mail jobs, activity tracking, planning/archive/rescheduling, financial recurrences and automation rules are paused after replacement. Review their targets and deliberately enable them again. Existing scoped API tokens expire; issue fresh tokens and reconnect clients deliberately. Every old browser session, open form, website session mapping and pending prepared action is invalidated. A PIN-protected profile requires unlocking again. This prevents an old approval or cached task ID from acting on an unrelated incoming record, or from forwarding newly received private data to another device.

Stop running Focus and Work timers before delivering or applying a snapshot. Incoming running timers are also rejected. Delivery uses `VACUUM INTO` for a consistent SQLite snapshot; the live database file is never copied. Exported snapshots are sanitized independently, without changing the sender's records. Pairwise X25519-derived keys feed the authenticated streaming encrypted-backup format. File length/hash is checked before atomic publication to the shared folder. The receiver checks authentication, the exact supported schema, archive path/size/hash limits and document references.

Before replacement, the existing encrypted-restore path takes a consistent local database snapshot and moves existing uploaded files into `data/backups/before-encrypted-restore-*`. Its restore journal rolls back both on interruption. Session invalidation and replay protection are written into the staged incoming database before activation, so they activate atomically with the restored records even if the process stops before responding. The local safety backup is unencrypted, like the rest of this profile's SQLite data; protect the computer accordingly. Automatic transport never applies a received write without review.

Real USB/cloud client delivery between two physical computers remains device acceptance; these local checks do not claim it.
