# Your own AI account in LifeOS

Open **Settings → Connect my AI account**, choose **Connect my account**, then **Open secure sign-in**. The official OpenCode website opens in your normal browser. Complete its sign-in and approve the displayed device code, then return to LifeOS. Choose your own account on that website; LifeOS never asks for your Google password. Your LifeOS account and OpenCode account are separate authorizations. A Google login to LifeOS alone cannot authorize OpenCode.

The commercial 1.9.5 installer requires this personal AI connection before sending a chat message. The dedicated conversation panel links to connection settings when needed; model/provider configuration is not added to the chat flow. The Windows worker independently verifies that a credential exists before it makes a commercial generation request. It still checks all input/output/cache prices and only sends to the verified zero-cost catalog. A connected paid account does not authorize paid model use in LifeOS.

Each local LifeOS profile has its own isolated OpenCode credential database under the existing per-profile runtime sandbox. The connection is saved by OpenCode's native OAuth API; LifeOS never exports/imports personal credentials, copies the developer's login, or ships a shared API key. It keeps only a boolean connection status in the profile's `ai/account.json`. AI tokens stay in the native local credential store, outside the personal database/document backup. Disconnect uses the native credential-delete API. It does not revoke every external session on the provider; revoke access on the official website if necessary.

The status record also binds the connection to the signed-in LifeOS account identifier. Switching LifeOS accounts on the same local profile cannot reuse the former customer's connection. Starting a new connection removes the previous native credential and requests fresh approval; checking status alone never relabels an old connection as the new user.

Sign-in uses a short-lived, password-protected server listening only on loopback, with the existing runtime and restricted configuration. Its official `device` OAuth method creates the one-time authorization. The native host opens only a current, unexpired HTTPS `opencode.ai` link from that queued job. Other hosts, credential-bearing URLs and alternate ports are rejected. Expiry and cancellation close the attempt and stop the temporary server. Switching workspace or locking LifeOS requests cancellation; closing the app terminates its workers through the Windows job object. No AI weights or extra authentication runtime are downloaded.

Provider limits remain authoritative. Different customer sign-ins are not a promise of independent unlimited quotas: a provider can limit an account, IP, model, organization or device. Login/logout and profile connection operations do not clear the existing cooldowns, and LifeOS does not create replacement accounts to evade limits. Once zero-cost capacity is exhausted, wait for the service to reset it. There is no automatic paid fallback.

The shared-key OpenRouter relay prototype was removed after the owner clarified the per-customer requirement. It was never deployed and no API key was configured. Official Google sign-in for the LifeOS website itself still needs an Orean Google OAuth client registration and is not part of this OpenCode connection. The existing email/password LifeOS login remains available.

References: [OpenCode authentication methods and credential storage](https://opencode.ai/v2/docs/cli/providers), [Console model access](https://opencode.ai/v2/docs/console/models/), and the [pinned v2.2.5 API contract](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/protocol/src/groups/integration.ts).
